Page-Level 2D KV Resharding for DCP + PD Disaggregation + CP Layer-Split

When Prefill Layer-Split Meets Decode Sequence Sharding: Correctness Guarantees for Cross-Node KV Transfer
sglang b300-glm52 · GLM-5.2-FP8 · 256 experts · 78 layers · CP=8 (layer-split) + DCP=4 + EAGLE

1. Motivation

When loading 4 LoRA experts + GLM-5.2 FP8 weights + EAGLE draft model simultaneously, the available KV cache memory per GPU on the Decode side is severely limited. On B300 (Blackwell Ultra, 288GB HBM3e), DCP=1 (no sequence sharding) allows only ~1.17M tokens of KV cache per rank (EAGLE draft model consumes extra memory; ~2.0M without EAGLE). This severely limits Decode concurrency: when multiple long-context requests (e.g., 500K–1M tokens) arrive simultaneously, insufficient KV cache capacity causes request queuing and TTFT degradation.

Configuration Choice: CP=8 + DCP=4. After balancing memory vs speed, we adopt Prefill-side CP=8 (8 CP ranks, each holding 78/8≈10 layers) + Decode-side DCP=4 (4 DCP ranks, each holding 1/4 pages). CP=8 maximizes Prefill-side memory savings from layer splitting, while DCP=4 provides 4× KV capacity expansion on the Decode side with acceptable TPOT overhead (~5–15%).All examples in this paper use CP=8 + DCP=4, but the algorithm is fully general—$N_{cp}$ and $N_{dcp}$ can be independently configured to any value.

With DCP=1 + EAGLE, KV capacity is only 1.17M tokens; DCP=4 scales to 4.67M (4×), DCP=8 to 9.34M (8×). TPOT overhead is only ~5–15% (DCP1→DCP8), while EAGLE at DCP8 reduces TPOT from 30.8ms to 8.6ms (3.6×).

The core value of DCP: with $N$ DCP ranks, KV cache capacity scales linearly by $N$×, while TPOT increases only ~5–15%. This means DCP=4 can serve 4× more concurrent long-context requests on the same hardware with minimal latency cost. EAGLE speculative decoding further reduces TPOT: at DCP=8, EAGLE brings TPOT from 30.8ms down to 8.6ms (3.6× speedup), achieving low latency while maintaining high concurrency.

Technical Challenge: DCP shards the sequence by page across multiple ranks on the Decode side, while the Prefill side uses CP Layer-Split (by layer). The two sharding dimensions are orthogonal, requiring page-level 2D reshard for KV transfer—simultaneously rearranging both layer and sequence dimensions, with correctness guarantees for cross-rank collectives (rank-invariant gates + size-broadcast + consensus prefix).

2. Problem Statement

In PD disaggregated inference, Prefill and Decode run on separate nodes, with KV cache transferred via mooncake RDMA. The two sides shard KV along orthogonal dimensions, forming a 2D reshard problem:

DimensionPrefill (CP Layer-Split)Decode (DCP)
Shard axisLayers(layer dimension)Sequence(page dimension)
Per-rank holdingsAll pages × owned 1/8 layers1/4 pages × all 78 layers
CP size8 (78 layers in 8 groups: 10×6+9×2)4(page by page_idx % 4)
Transfer granularitypage-level(64 tokens/page, physical page_size)

Let the Prefill side have $N_{cp}$ CP ranks and the Decode side have $N_{dcp}$ DCP ranks. Each Prefill CP rank $r$ holds layer set $\mathcal{L}_r \subset \{0, \ldots, 77\}$ and all pages $\mathcal{P}_{\text{full}}$. Each Decode DCP rank $d$ holds page subset $\mathcal{P}_d = \{p \mid p \bmod N_{dcp} = d\}$ and all layers. Transfer target: for each path $(r, d)$, transfer $\mathcal{L}_r \times \mathcal{P}_d$ KV from Prefill rank $r$ to Decode rank $d$.

2D Reshard Target
$$\forall r \in [0, N_{cp}), \; \forall d \in [0, N_{dcp}): \quad \text{Transfer}(\mathcal{L}_r, \; \mathcal{P}_d, \; r \to d)$$

4. CP Layer-Split (Prefill Side)

4.1 Layer Assignment

78 Transformer layers are contiguously partitioned across CP ranks. $\lfloor 78/8 \rfloor = 9$, remainder $78 \bmod 8 = 6$; the first 6 ranks get 10 layers ($9+1$), the last 2 get 9:

Layer Range
$$\mathcal{L}_r = \left[ r \cdot \left\lceil \frac{L}{N_{cp}} \right\rceil, \;\; (r+1) \cdot \left\lceil \frac{L}{N_{cp}} \right\rceil \right), \quad r = 0, \ldots, N_{cp}-1$$
# Layer assignment: 78 layers → 8 CP ranks function cp_layersplit_layer_range(N_layers, N_cp, r): per ← N_layers div N_cp # 78 / 8 = 9 (remainder 6) return [r × per, (r+1) × per) # half-open interval # Result: # Rank 0: L[0, 10) → 10 layers # Rank 1: L[10, 20) → 10 layers # Rank 2: L[20, 30) → 10 layers # Rank 3: L[30, 40) → 10 layers # Rank 4: L[40, 50) → 10 layers # Rank 5: L[50, 60) → 10 layers # Rank 6: L[60, 69) → 9 layers (remainder) # Rank 7: L[69, 78) → 9 layers (remainder) # KV pool: per+1 slots per rank (owned layers + 1 transient for broadcast) function local_layer_count(N_layers, N_cp, r): [start, end) ← cp_layersplit_layer_range(N_layers, N_cp, r) return (end - start) + 1 # +1 = transient slot

4.2 Prefix KV Broadcast: Size-Broadcast Protocol

Non-owner ranks need prefix KV from the owner rank. HiCache local-only prefetch may cause prefix lengths to differ across ranks. The size-broadcast protocol ensures all ranks participate in the same number of NCCL broadcasts:

Size-Broadcast Protocol
$$n = |\text{slots}_{\text{owner}}| \quad \text{(broadcast } n \text{ to all ranks first)}$$ $$\text{if } n = 0: \;\; \forall r: \text{skip} \quad (\text{consistent})$$ $$\text{if } n > 0: \;\; \forall r: \text{broadcast } n \text{ KV elements} \quad (\text{all ranks participate})$$
function broadcast_owner_layer_prefix(layer_id, forward_batch, kind): owner ← cp_layersplit_owner_rank(layer_id, ...) prefix_lens ← forward_batch.extend_prefix_lens_cpu # None guard: normalize to zeros (prevent per-rank None divergence) if prefix_lens = None: prefix_lens ← zeros(len(req_pool_indices)) # Step 1: compute element count count ← |prefix_slots| # Step 2: broadcast count to ALL ranks (1-element, mandatory) n_tensor ← tensor([count]) broadcast(n_tensor, src=owner, group=cp_group) n ← n_tensor.item() # Step 3: consistent skip or consistent broadcast if n = 0: return # ALL ranks skip # Step 4-5: broadcast n KV elements; non-owner writes to transient_pool

5. DCP (Decode Side)

5.1 Page-Level Round-Robin Sharding

Decode-side KV cache is allocated in pages (64 tokens each) via round-robin. The DCP allocator size is $M \times N_{dcp}$ (virtual slots), with each DCP rank holding $1/N_{dcp}$ of pages:

DCP Page Ownership
$$\text{owner}(p) = p \bmod N_{dcp}, \quad p \in \{0, \ldots, M \cdot N_{dcp} - 1\}$$ $$\text{slot}_{\text{local}}(p) = \left\lfloor \frac{p}{N_{dcp}} \right\rfloor \in \{0, \ldots, M - 1\}$$

5.2 DCP Attention: All-Gather + LSE Merge

Each DCP rank holds only $1/N_{dcp}$ of KV pages; attention output requires all-gather + LSE merge to combine:

DCP Attention Output Correction
$$O_{\text{full}} = \text{AllGather}(O_{\text{local}}) \quad \text{(concat along seq dim)}$$ $$\text{LSE}_{\text{merged}} = \log\!\left(\sum_{d=0}^{N_{dcp}-1} \exp(\text{LSE}_d)\right) \quad \text{(merge across DCP ranks)}$$

5.3 Communication Overhead Analysis

DCP introduces two sources of communication overhead per decode step:

Overhead Breakdown (DCP=4, TP=8, 78 layers)

OperationFrequencyVolume per stepImpact
All-gather KVPer attention layer~78 × (hidden_dim × seq_len / N_dcp) bytes~3× extra KV read vs DCP=1
LSE mergePer attention layerN_dcp scalars (negligible)O(N_dcp) all-reduce
PD transfer (2D reshard)Per request (prefill→decode)Full KV × 1/N_dcp pages per path32 paths (8 CP × 4 DCP), parallel via mooncake RDMA

The 32 PD transfer paths execute in parallel—each Prefill CP rank independently sends to each Decode DCP rank via mooncake RDMA, so transfer latency ≈ single-path latency (not 32×). The dominant overhead is the per-step all-gather in DCP attention, which grows linearly with N_dcp but is amortized by EAGLE's speculative decoding (5 steps × 6 draft tokens = 30 tokens verified per step, with accept rate ~39% reducing effective decode steps).

TTFT impact: PD disaggregation adds one RTT for KV transfer (mooncake RDMA, ~0.5-2ms for typical 4K-32K token sequences). The 2D reshard adds page-level filtering overhead (~0.1ms for 256 pages × 4 DCP ranks), negligible compared to prefill compute time. Measured TTFT on B300: 0.38s (DCP=4, 1K input) to 1.7s (DCP=4, 32K input), dominated by prefill compute, not transfer. For 500K+ token sequences, DCP=4's 4× KV capacity is essential—a single 500K request consumes ~7.8K pages, exceeding DCP=1's 1.17M token capacity per rank.

6. Page-Level 2D Resharding (Core)

6.1 Design Evolution: From Token-Level to Transfer-Time Sharding

The current design—page-level sharding during RDMA transfer—was not the initial approach. The design went through two iterations:

  • Initial approach: decouple sharding from transfer. The original idea was to shard KV at the token level for maximum flexibility, and keep the sharding logic separate from the PD transfer. Concretely, Prefill would transfer the full, unsharded KV to Decode via RDMA, then Decode would run an inplace_shard_dcp pass to redistribute tokens into the DCP rank layout. This is simple to reason about—the transfer knows nothing about DCP—but wasteful: the full sequence is transferred to every DCP rank (each rank receives $N_{dcp}\times$ the data it needs), only to discard $\frac{N_{dcp}-1}{N_{dcp}}$ of it during the in-place reshard.
  • Final design: shard during transfer. We realized that the transfer itself is the natural sharding point. Since mooncake RDMA operates at page granularity (the physical page_size = 64 tokens), and DCP already shards by page (owner(p) = p mod N_dcp), we can filter page indices before the RDMA write—sending only the $1/N_{dcp}$ pages each DCP rank actually needs. The RDMA write lands directly in the correct DCP-local slot, eliminating the post-transfer reshard entirely (dcp_kv_shard_pages = None).
Key insight: The transfer unit is the sharding unit. Because RDMA transfers at page granularity and DCP shards by page, filtering at the source (Prefill) naturally produces the correct destination (Decode) layout—no intermediate full-sequence copy, no post-processing. The sharding is not a separate step; it is the transfer itself.

6.2 Page Index Filter

This is the core of 2D reshard. Before RDMA send, the Prefill side applies DCP filtering to page indices per layer:

filter_kv_indices_for_dcp_rank
$$\text{mask}(p, d) = \mathbb{1}\!\left[p \bmod N_{dcp} = d\right]$$ $$\text{filtered}(p, d) = \left\lfloor \frac{p}{N_{dcp}} \right\rfloor \quad \text{(compress to local slot)}$$ $$\mathcal{P}_{r \to d} = \left\{ \left\lfloor \frac{p}{N_{dcp}} \right\rfloor \;\middle|\; p \in \mathcal{P}_{\text{full}}, \; p \bmod N_{dcp} = d \right\}$$
# Input: kv_indices = prefill-side global logical page indices (full set) # Output: only pages owned by DCP rank d, mapped to local physical slots function filter_kv_indices_for_dcp_rank(kv_indices, N_dcp, d): if N_dcp ≤ 1: return kv_indices mask ← kv_indices mod N_dcp = d # page ownership test return kv_indices[mask] div N_dcp # compress to local slot
Correctness Guarantee:
① kv_indices are prefill-side global logical page indices (slot = pos, DCP allocator size = $M \times N_{dcp}$)
② mask = page_idx % N_dcp == d: keep only pages belonging to the target decode rank
③ // N_dcp: compress global page slot to decode-side local physical page slot
④ RDMA write lands directly in decode's DCP sharded layout, no post-processing needed

8. EAGLE + DCP Adaptation

EAGLE speculative decoding introduces a draft model that runs in the same process as the target model. The target KV pool is DCP-sharded (each rank holds 1/N_dcp of pages), but the draft model needs the full sequence to generate draft tokens. This creates a fundamental tension:

  • Target model: runs under DCP, sees only 1/N_dcp of KV pages, uses all-gather + LSE merge for attention output.
  • Draft model: must see the full KV to predict next tokens. If it ran under DCP, the draft tokens would be inconsistent across DCP ranks (each rank only sees 1/4 of the context).

Solution: the @dcp_disabled() context manager temporarily disables DCP for the draft model's forward pass. The draft model uses a separate, non-sharded KV pool with draft_pool_token_multiplier = dcp_size (4×) to allocate enough capacity for the full sequence. After draft generation, the target model verifies draft tokens under DCP mode—each DCP rank independently verifies its 1/N_dcp shard of the draft tokens, then all-gather merges the acceptance results.

# eagle_worker_v2.py @dcp_disabled() # temporarily disable DCP for draft model function forward_draft(...): # draft model sees full sequence, not affected by DCP sharding # target model verifies draft tokens under DCP mode ... # draft pool token allocation accounts for DCP multiplier draft_pool_token_multiplier ← server_args.dcp_size # 4×
