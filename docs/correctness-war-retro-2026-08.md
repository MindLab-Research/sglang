# GLM-5.2 PD 集群正确性问题排查记录（2026-08-18 ~ 08-22）

## 摘要

2026 年 8 月 18 日至 22 日，GLM-5.2 PD 分离推理集群出现持续性输出乱码问题。
排查历时五天，累计 64 个 commit（41 个修复）、19 篇调查文档，先后排除采样器、
解析器、EAGLE、LoRA、CP 等多个组件，最终定位到 DCP decode 索引器的两个缺陷
（`5974a4fc56`）。排查过程中还修复了 CP×LoRA pad 行 NaN 毒化（`12cda1cd60`）、
draft 虚拟 id 域错配（`9db63a6abb`/`371a991947`）、MoL 多适配器乱码四层
（`f070d3d466`/`d56db6bea5`/`12cda1cd60`/`37fae98ed7`）等多个独立缺陷。本文记录
完整的排查路径、根因分析与方法论。

---

## 一、系统架构

本集群为 GLM-5.2-FP8 的 PD 分离推理系统，涉及以下关键组件，后续所有问题均源于
这些组件的"坐标系统"不一致：

- **PD 分离**：prefill（预填充）与 decode（解码）运行在不同节点，通过 mooncake
  RDMA 传输 KV Cache。prefill 是计算密集型，decode 是延迟敏感型。
- **KV Cache**：模型为每个 token 计算并存储记忆向量，长对话可达数百 GB。编号、
  存放、运输的任何错位都会导致模型读到错误记忆。
- **TP / CP / DCP**：三种并行切分方式。TP（张量并行）切权重；CP（上下文并行）
  切序列，prefill 使用；DCP（decode 上下文并行）切 KV Cache，decode 使用。三者
  的行对齐和编号一致性是正确性的基础。
- **DSA 稀疏注意力 + 索引器**：为长上下文建索引，索引器给所有页打分，挑出最相关
  的 2048 页供大模型细读。**索引器是本次终局根因所在。**
- **EAGLE 投机解码**：草稿模型一次猜 6 个 token，目标模型批量验证。健康指标
  accept length 正常区间 2.2~3.2。
- **MoL（Mixture-of-LoRA）**：底座模型 + L0~L3 四个 LoRA 适配器，请求体 `lora_path`
  字段指定。LoRA delta 在数十层网络的每次矩阵乘法中插入，行号错位即灾难。
- **cuda graph**：将一步计算录制后整段重放，要求形状和编号固定，填错位置导致
  静默数据错乱。
- **radix / HiCache**：前缀树缓存 + 磁盘分层缓存，复用脏数据是错误放大器。

## 二、故障现象

排查期间观察到**两种性质不同的乱码签名**，最初被混为一谈，后期才区分清楚：

### 2.1 签名 A：中途乱码（DCP index_k 缺陷）

- **表现**：模型输出到一半突然开始循环输出模板记号（`<|...|>`），或输出数字汤
  （`"id":3, "1, "0, "1, "0, "4, "id": "se, "1, "2, "fatal: true`）。
- **置信度异常**：强制注入 logprobs 后，乱码 token 的置信度 99% 以上，均为模型
  第一选择——说明不是采样随机性，而是前向计算的输入（KV Cache）已错误。
- **内容回声**：乱码内容常为上下文中数百 KB 之前某次工具调用的参数原样复制，
  说明注意力读到了错误位置的旧记忆。
- **概率性**：同一请求重放，乱码率 30%~50%；命中缓存的请求基本干净，缓存被挤占
  需重算的请求易乱。
- **自愈性**：乱码后可自行恢复；flush 缓存或重启 decode 进程可缓解。

### 2.2 签名 B：首 token NaN 乱码（CP×LoRA pad 行缺陷）

- **表现**：请求结果从首个 token 开始即为乱码，输出形如 `!0,0,0,0,1,0,1,`
  （感叹号 + 数字汤）。
- **首 token 恒为 id 0**：`output_ids[0] == 0`，logprob 返回 None。根因是 logits
  为 NaN，`argmax(NaN) = 0`，模型选了 0 号 token（词表中为 `!`）。
- **高复现率**：filler prompt 电池测试乱码率 13-31/32（40%~97%）。
- **base 模型永远干净**（0/32 × 多轮）。
- **状态持续**：乱码后状态持续（"污染扩散"），非偶发。

两种签名的区别至关重要：签名 A 是"读到错位置的旧记忆"（索引错位），签名 B 是
"前向计算本身算出 NaN"（pad 行毒化）。排查方向完全不同。

## 三、排查过程

### 3.1 LoRA 嫌疑线（8 月 18-21 日）

初期只有 LoRA 请求乱码，自然优先排查 LoRA。此线挖出四个真实缺陷，每个修完乱码
均减轻，但均非终局根因：

**缺陷 1：cuda graph 槽位残影**（`f070d3d466`）。base + L0~L3 共五个 uid 超过
`max_loras_per_batch=4`，LRU 驱逐时 cuda graph 的 `token_lora_mapping` 尾部残留
旧 adapter id，导致后续请求用错包，且随 graph 重放持续传染。移植上游 #29468 修复。

**缺陷 2：HiCache 缓存键缺 LoRA id**（`d56db6bea5`）。缓存键只看对话内容，未掺
adapter 名字，不同租户用不同适配器发相同开头会共享 KV Cache，造成跨 adapter 污染。
修复：缓存键从根上掺入 adapter 名字。

**缺陷 3：CP pad 行被施加 LoRA delta → NaN 毒化**（`12cda1cd60`）。此缺陷的定位
过程使用了两层二分组合实验，详见 §3.2。

**缺陷 4：槽位逐出 churn 毒化在途长请求**（`37fae98ed7`）。逐出策略偏向"保住 LoRA、
牺牲 base"，导致 35 万字长请求做到一半适配器被换。对照实验：4 槽配置乱 2 次、
逐出 5 次；5 槽配置 0 乱 0 逐出，唯一变量为槽数。

此线还有一个方法论教训：单机测试全过、PD 集群崩溃，追查 20 小时后发现是生产
prefill 启动脚本缺少 `--lora-use-virtual-experts` 参数，走了未加固的 classic
kernel 路径。**对照实验前必须逐条 diff 两边启动参数。**

### 3.2 CP × LoRA：两层二分组合实验（8 月 21 日）

此段是整个排查中方法论最严谨的部分，示范了如何用两层二分组合实验将模糊的
首 token 乱码定位到具体的两层 LoRA 计算组合。

#### 3.2.1 第一层二分：CP × LoRA 2×2 组合

将 CP 和 LoRA 两个开关做笛卡尔积，四种组合各跑一轮（相同请求、权重、温度）：

| 组合 | CP | LoRA | 结果 |
|---|---|---|---|
| base | 关 | 关 | 干净（0/32） |
| 纯 LoRA | 关 | 开 | 干净（32/32） |
| 纯 CP | 开 | 关 | 干净 |
| CP + LoRA | 开 | 开 | 乱码（13-31/32） |

只有第四种乱码。此结果排除了所有单因素假设：不是 CP 本身缺陷，不是 LoRA 本身
缺陷，而是两者的组合交互。问题出在两个子系统的接缝上。

#### 3.2.2 第二层二分：LoRA 模块族组合

CP×LoRA 定罪后，需进一步定位是 LoRA 的哪些模块与 CP 组合出问题。使用运行时
模块族二分工具（`SGLANG_LORA_FAMILY` 环境变量），无需重新打包 adapter 权重，
一个 env 切换即可选择只对哪些模块族施加 LoRA delta。

四组单臂（kv_a / q_b / o_proj / kv_b）各自干净。两两组合：

| 组合 | 结果 |
|---|---|
| **kv_a + o_proj** | **乱码（13/32）** ← 最小犯罪组合 |
| kv_a + q_b | 干净 |
| kv_a + kv_b | 干净 |

**kv_a + o_proj 是最小犯罪组合**——单独均不坏，合在一起才坏。原理：

- **kv_a**（K/V 投影）写出 K、V 存入 KV Cache，包括 pad 行的 K/V 槽。若 pad 行被
  施加 LoRA delta，delta 作用于 pad 行的垃圾激活（freed-memory 残留，量级 ~1e-9），
  浮点运算后可能产生 NaN，写入 pad 行的 KV 槽。
- **o_proj**（输出投影）将 attention 输出写入 hidden state。若 K/V 含 NaN（来自
  kv_a 写的 pad 行槽），attention 输出 `softmax(Q@K^T)@V` 即为 NaN，o_proj 将 NaN
  传播到下一层 hidden。
- 单独 kv_a：NaN 写入 K/V 槽，但 o_proj 无 delta 时 NaN 可能被残差连接稀释，
  不一定稳定传播。
- 单独 o_proj：K/V 干净，attention 输出有限，o_proj delta 作用于有限值不产生 NaN。
- **只有 kv_a + o_proj 同时有 delta**：kv_a 产生 NaN 源，o_proj 稳定传播到 hidden，
  下一层全 NaN → logits NaN → argmax=0 → `!`+数字汤。

#### 3.2.3 根因：pad 行被施加 LoRA delta → NaN 毒化真实行

根因分三步：

**第一步：CP 产生 pad 行。** CP round-robin 将 batch 切成 cp_size=8 段，token 数
非整除时补齐：

```
N_real = 29,  cp_size = 8
N_pad  = cp_size - (N_real % cp_size) = 8 - 5 = 3
N_batch = N_real + N_pad = 32   （pad 行 = [29, 30, 31]）
```

**第二步：pad 行被归属给最后一个请求，施加完整 LoRA delta。**
`_cp_shard_row_request_ids` 将 pad 行归属给最后一个请求（而非丢弃），shard 视图的
LoRA segments 对 pad 行施加完整 adapter delta。pad 行激活为 freed-memory 残留
（~1e-9），delta 作用后产生 NaN，写入 pad 行的 KV 槽：

```
delta_output = W_down @ activation(~1e-9) @ W_up  →  inf/nan
```

**第三步：NaN 经 KV 传播到真实行。** pad 行与真实行在同一 attention 的 KV 中。
下一层真实 query 计算 `Q@K^T` 时，K 含 pad 行的 NaN：

```
scores = Q @ K^T          # K 的 pad 行为 NaN → scores 对应列 = NaN
attn   = softmax(scores)   # NaN 传播 → attn = NaN
output = attn @ V          # V 的 pad 行也为 NaN → output = NaN
hidden  = hidden + o_proj(output)   # NaN 进入 hidden
```

逐层 dump 证据（`--debug-tensor-dump`）：

- layer-7 MoE gate：NaN 仅在 gather 后 32 行的 pad 行 [23, 27, 31]；
- layer-8 attention 输出：4 个真实行全 NaN——NaN 从 pad 行 KV 槽经 attention 传播
  到所有真实行；
- logits：全 NaN → `argmax(NaN) = 0` → token id 0 → `!`+数字汤。

MLA-AUDIT 探针（`SGLANG_MLA_AUDIT=1`）确认：kv_a+o 组合下 audit 计数 7821
（正常为 0），hidden=NaN 从 layer 1 起出现。

**随机性来源**：pad 行激活为 freed-memory 残留，内容取决于分配器复用了哪块内存，
因此同一请求重放有时 NaN 有时不 NaN，复现率 13-31/32 波动。

#### 3.2.4 修复

修复（`chunked_backend.py`，commit `12cda1cd60`）：pad 行保留 -1 哨兵，映射到
adapter slot 0（base 槽，`lora_ranks[0]==0`，权重恒零）。所有 LoRA kernel 对
rank-0 segment 早退 no-op，pad 行收到零 delta，KV 槽为 base 权重算出的有限值。
segments 保持覆盖全行（`covered == x_rows` 不变量）。

第一版尝试将 pad 行排除出 segments（permutation 短于 x），warmup 即 IMA
（absorbed step kernels 未验证过该结构），回退为 slot-0 映射。

验收（1101/1100 测试对，完整 L0 + CP on + 生产 flags）：电池测试（12 filler +
20 topic）×3 轮 0/96 乱码，MLA-AUDIT 计数 0。

### 3.3 draft 崩溃与 accept 断崖（8 月 19-20 日）

此线独立于乱码，但揭示了 DCP 的"虚拟 id 域"体系——终局根因所在。

CUDA Xid 31 崩溃（GPU 非法地址访问）的根因：草稿模型每次开猜前从 `req_to_token`
表抄录"笔记存储位置"清单，偶尔抄到撕裂的旧数据，拿到超出池容量的垃圾格子号。
演化三段式：第一阶段直接崩溃；第二阶段只消毒写入端，不崩但垃圾格子号混入空闲
列表，分配器永久中毒，accept 从 3.0 降至 1.0 不恢复；第三阶段在源头钳制合法范围
（`0e5f7704e1`）。

随后 accept 降至 0.07，根因为**虚拟 id 域错配**：DCP=4 的 decode 中 `req_to_token`
存统一虚拟门牌号，所有写入和读取须做虚拟→物理换算且只能换算一次。代码中有的
地方换算两次，有的将合法虚拟号当越界垃圾消毒，merge 上游版本时还将草稿池从
7.4M 缩至 1.85M，导致虚拟门牌大面积越界。三张补丁（`9db63a6abb`/`371a991947`）
统一为"虚拟号全程保留，只在碰物理池时换算"。

此线还纠正了一个认知：单请求 accept 5.9（每猜必中）非"状态好"，而是复读机病征
（草稿沿退化轨道走，目标模型全盘接受，输出全重复）。健康区间 2.2~3.2。

draft 线修完后崩溃停止，accept 回到健康区间，但乱码仍在。关键发现：**关闭 EAGLE
后乱码仍在**，排除 EAGLE。

### 3.4 消融实验推翻前提（8 月 22 日上午）

8 月 22 日凌晨至上午，三组消融实验（每组：改配置→重启→预热 5 分钟→灌相同流量，
一轮 20-40 分钟，公网 RTT 当天劣化至 7 秒）：

**实验 1：base 模型也乱。** 录制代理将流量强制改写为不带 LoRA 的纯底座请求，乱码
照样复现。"只有 LoRA 有问题"的前提被否定。

**实验 2：关闭 CP，仍乱。** CP 行对齐嫌疑最大（上游源码注释承认"CP 和多请求批次
有精度问题"），且 CP 整除门修复在测试对上"28 连发零乱码"。但 CP 整个关闭后乱码
依旧。该"28 连发零乱码"实为撞上另一缺陷的静默期。CP 被排除。

**实验 3：关闭 DCP，干净。** decode 从"四组各管四分之一 KV"退回"一组管全部"，
同样流量不再乱码。多轮反复验证，结论稳定。**DCP 定罪。**

同日还澄清一桩误判：流式输出间隔增大看似"decode 性能断崖"，实际是公网劣化
（0.37MB/s）叠加取证代理强制注入 top-5 logprobs（载荷放大 3-5 倍）所致，引擎
吞吐正常。**判断"变慢"须区分计算延迟与传输延迟。**

### 3.5 DCP 双缺陷定位（8 月 22 日下午）

DCP 定罪后，五个并行调查 agent 分别分析注意力元数据生命周期、Triton kernel
数学、KV 传输与页归属、索引构建链路、git 历史考古，三路独立收敛到索引器周边的
两个缺陷。

## 四、根因分析

### 4.1 缺陷 A：index_k 全域 owner 换算缺失（主因）

DSA 索引器为笔记每一页计算一张"索引卡片"（index_k），存入池中供打分挑页。
DCP=4 时每张卡的存放位置须做虚拟号到本组物理槽位的换算。旧代码有一个优化判断：
"小于本组池子大小的编号，肯定已是本地物理槽位，直接存"。

此判断错误：分配器发放的虚拟号从 0 递增，本组池子大小为 1.85M。进程刚启动、
水位低时，头几个大请求的虚拟号全部小于 1.85M，全部走直通分支，全部未换算，
索引卡片存错格子。索引器用错位卡片打分，稀疏注意力挑出的 2048 页为错误页，
模型读错笔记。

该缺陷的隐蔽性：

- 越界但不越到非法区（错格子也是合法格子），不崩溃、不报警、日志正常；
- 水位涨过 1.85M 后直通分支自然失效，换算分支接管——缺陷自愈。这同时解释了
  "重启 decode 能缓解"（水位清零重新进入坏窗口）、"长请求尾部自愈"（尾部 token
  的卡片在水位越过线后写入）、"概率性"（取决于请求落在水位线哪侧）；
- 同时影响 base 和 LoRA，但 LoRA 流量长上下文多、缓存挤占频繁触发重算，看起来
  "只有 LoRA 乱"，误导排查三天。

修复（`5974a4fc56`）：去掉优化判断，所有编号无条件做完整换算，与主 KV 写入路径
用同一套公式。诊断计数器移到修复动作之前（原计数器在修复之后，恒为零）。

### 4.2 缺陷 B：topk -1 空位钳到 slot 0（次因）

索引器每行交出 2048 个页号。DCP=4 时每张卡只有四分之一的页可挑，上下文短于
约 52 万 token 的请求本组页数不足 2048，清单留空位（值 -1）。正确处理是让注意力
跳过空位，但快速路径将清单直接喂给 NVIDIA trtllm kernel，下游保底操作将所有 -1
钳到 0 号格子（存无关内容 KV）。

对照实验定罪：让某组一行页都不拥有（清单全空），kernel 返回归一化系数 0 而非
负无穷，证明它对每个空位都做了注意力计算，无任何跳过。最坏情况：四分之三的
注意力预算花在同一个无关页上。

修复：空位不再钳 0，改指向本行第一个有效页（打分最高的页），多算几次自己的
头名种子，数学上仅权重略偏，不引入外部内容。

### 4.3 两个缺陷的协同

缺陷 A 导致索引卡片存错格子（低水位窗口），缺陷 B 导致空位读无关 KV（短上下文
请求）。两者叠加：低水位 + 短上下文的请求同时命中两个缺陷，乱码率最高。修复后
测试对（DCP=4 + EAGLE 开）37%~50% 乱码流量持续干净，当天部署生产 1P2D 公网验证
通过。

- 监控判据：`DSA-SLOT-OOB window_oob` 应为 0 或低值，无 `DIVERGENCE`/OOM 行，
  accept len 2.2~4.5。

### 5.3 部署插曲

两台 decode 在新进程运行 8.5 分钟后同时退出（查登录日志、OOM 记录、定时任务均
非人为，堆栈被下次重启覆盖丢失，成为悬案，已改流程要求重启前备份日志）；一次
"重启 proxy"实际未杀掉旧进程（端口匹配未生效），旧 proxy 一直健康，虚惊一场。

## 六、方法论与教训

1. **症状同质化**：三个不同层面的缺陷（cuda graph 残影、缓存串柜、索引错位）
   产生的乱码外观一致。修掉一个症状减轻但不消失，无法判断是"修得不彻底"还是
   "另有缺陷"。先后三次认为结案，三次重新开案。

2. **概率性是误判放大器**：复现不稳定时，"修完 N 连发没乱"不能下结论——可能
   撞进另一缺陷的静默窗口（CP 整除门那次正是如此）。后期立规：任何修复验证须先
   让系统进入"易乱"状态（低缓存水位、长上下文、强制重算），再谈干净。

3. **两种乱码签名须区分**：签名 A（中途乱码，读到错位置旧记忆）与签名 B（首 token
   NaN，前向计算本身算出 NaN）方向完全不同，不能混为一谈。

4. **组合实验定位组合缺陷**：单因素实验无法定位"组合才坏"的缺陷。CP×LoRA 2×2
   矩阵排除所有单因素假设，LoRA 模块族二分（`SGLANG_LORA_FAMILY`）将范围从
   "几十层 LoRA"缩小到"kv_a+o_proj 两层 delta 同时作用于 pad 行"。

5. **运行时模块族二分**：一个 env 切换即可选择施加 delta 的模块族，零 adapter
   重打包，将"哪层坏"的验证从小时级降到分钟级。

6. **逐层 dump 行级 NaN 分析**是定位毒化传播的金标准：pad 行 NaN → 真实行 NaN
   的传播链一眼看出毒化方向。

7. **对照实验前先 diff 启动参数**：单机测试全过、PD 集群崩溃，追查 20 小时后发现
   是生产脚本缺少 `--lora-use-virtual-experts`。"同代码"假设在本案为假，一个 flag
   切换了整条 kernel 路径。

8. **判断"变慢"须区分计算延迟与传输延迟**：公网劣化 + logprobs 载荷放大制造了
   假的"性能断崖"，引擎吞吐实际正常。
