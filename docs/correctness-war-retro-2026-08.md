> 写给所有同事，包括不搞推理引擎的同学。不需要懂 CUDA，不需要懂分布式，
> 只需要知道：我们在给一个大语言模型搭一套跑在多台 GPU 机器上的服务，
> 而这套服务最近半个月一直在"随机说胡话"。这篇文章讲我们怎么把原因挖出来的，
> 中间走了多少弯路，以及为什么这么难。

## 一、我们在跑一个什么样的系统

先把零件讲清楚。后面所有的坑，都是这些零件的"坐标系统"对不上造成的。

**PD 分离。** 用户发来一条长消息，模型处理它分两步：先通读全文做笔记（叫
prefill，预填充），再一个字一个字往外吐（叫 decode，解码）。这两步的脾气完全
不同——prefill 是重活，吃算力；decode 是碎活，吃延迟。所以我们干脆用两拨机器：
一波专门读文章做笔记，一波专门吐字。笔记做完了，用 RDMA 网卡（一种延迟极低的
专用网络，我们用的实现叫 mooncake）整包运给吐字那波机器。

**KV Cache 就是那份笔记。** 模型每读一个字，都会为它算出一份"记忆向量"存起来，
后面吐字的时候要反复回头查。一个 50 万字的长对话，这份笔记有几百 GB。所以笔记
怎么编号、怎么存放、怎么运输，是整个系统最容易出事的地方。

**TP / CP / DCP，三种"切蛋糕"方式。** 一层神经网络太大，一张卡放不下，怎么办：
- TP（张量并行）：把权重竖着切开，八张卡各拿一条，算完拼起来。最老牌，最稳。
- CP（上下文并行）：文章太长读不完，把文章撕成八段，每张卡读一段，最后把各段
  的理解拼起来。问题在于：拼的时候每张卡拿出的行数、顺序必须严格对齐，差一行
  就全错。prefill 用它。
- DCP（decode 上下文并行）：吐字的时候，把那份几百 GB 的笔记切成四份，四组卡
  各保管四分之一。吐每个字都要四组同时查自己那份再汇总。decode 用它。

**DSA 稀疏注意力 + 索引器。** 笔记太长，每个字都全文查一遍太慢。所以我们给笔记
建了个索引：先让一个小的"索引器"给所有页打分，挑出最相关的 2048 页（GLM-5.2
的配置），大模型只细读这 2048 页。**这个索引器就是本次事故的真凶藏身处。**

**EAGLE 投机解码（就是我们说的 draft）。** 吐字慢是因为每吐一个字都要跑一遍
大模型。EAGLE 的思路：带一个小的"草稿模型"，一次猜 6 个字，大模型一批验证，
猜对几个就白赚几倍速度。衡量它健康不健康有个指标叫 accept length（平均猜对
几个），正常 2 到 3。它还有自己的一份小笔记（draft KV pool）。

**MoL：LoRA 技能包。** 底座模型是通才，线上不同租户要不同的"技能包"（LoRA
适配器，L0 到 L3）。请求里带 `lora_path` 字段就背上哪个包。包不大（rank 16），
但要在几十层网络的每次矩阵乘法里插一小脚，插入的时机和行号错一格就是灾难。

**cuda graph。** GPU 每步计算要 CPU 下几百条指令，开销大。cuda graph 的做法是
把一步"录下来"，以后直接整段重放。代价是：录的时候所有的形状、编号都是定死
的，重放时要小心把新数据"填"回旧形状里，填错位置就是静默的数据错乱。

**radix / HiCache 缓存。** Agent 类用户的请求有个特点：每轮对话都带着之前全部
历史。那之前算过的笔记直接复用就行。radix 是前缀树缓存，HiCache 再加一层磁盘。
复用是省钱，但"复用了脏数据"就是灾难放大器。

这套东西单拎出来每个都成熟。叠在一起，就是十几个独立的编号系统（token 序号、
页号、卡内槽位号、虚拟页号、缓存版本号……）在同时运转。**任何一个环节把 A 编号
当 B 编号用，模型就会读错记忆，然后一脸自信地胡说八道。**

## 二、症状：一个会撒谎的 bug

8 月中旬开始，线上 MoL 流量出现"乱码"。具体长这样：模型输出到一半，突然开始
循环吐模板记号（`<|...|>`），或者吐一锅数字汤：
`"id":3, "1, "0, "1, "0, "4, "id": "se, "1, "2, "fatal: true`。

一开始只有 LoRA 请求乱，大家自然怀疑 LoRA。但真正让人头疼的是它的四个特征：

1. **它是"自信地错"。** 我们给请求强制注入 logprobs（让服务端顺便报出模型对每个
   字的置信度），发现乱码那几个字，模型置信度 99% 以上，都是它的第一选择。
   这说明不是采样手抖抽到了烂签，是前向计算本身算出了错误的结果——它的输入
   （笔记）就已经是错的。

2. **它抄自己。** 乱码内容不是随机噪声，经常是**把自己上下文里几百 KB 之前某个
   工具调用的参数原样抄出来**。比如它该输出一个读文件的命令，输出的却是几小时前
   某次搜索的关键词。这说明注意力读到了"错误位置的旧记忆"。

3. **它是概率性的。** 同一个请求重放，有时干净有时乱，比例大概 30% 到 50%。
   而且命中缓存的请求基本干净，缓存被挤掉、需要重算的请求容易乱。

4. **它会自愈。** 乱着乱着又恢复正常了；flush 一下缓存能救；重启 decode 进程
   能明显缓解一阵。

现在回头看，这四条特征几乎就是最终答案的画像（读到错页 → 概率性分配 → 水位
越界后自愈）。但在当时，每一条都同时符合好几种假设，**症状是会撒谎的**。

## 三、第一轮排查：LoRA 嫌疑线（8 月 18-21 日）

既然"只有 LoRA 乱"，就先把 LoRA 排查个底朝天。这条线挖出了四个**真实存在**的
bug，每一个都有实锤，每一个修完乱码都减轻，但没有一个是最后的根因。

**Bug 1：cuda graph 里的槽位残影。** 五个技能包（base + L0~L3）挤 4 个槽位，
逐出旧的换新的时候，cuda graph 里记录的"每个 token 用哪个包"的映射表尾部没清
干净，残留的旧编号让后来的请求用错了包，而且用错的状态会随 graph 重放一直
传染。这是上游 sglang 也踩过的坑（#29157/#29468），我们移植了修复（`f070d3d466`）。

**Bug 2：缓存柜没贴名字。** HiCache 的缓存键只看对话内容，**没掺 LoRA id**。
两个租户用不同技能包发了一模一样的开头，结果共享了同一份笔记——L0 的记忆被
L1 拿去用了，直接精神分裂。修复：缓存键从根上掺进 adapter 名字（`d56db6bea5`）。

**Bug 3：凑数的假行挨了真刀。** CP 把文章撕成八段时，行数除不尽要补几行假数据。
这些假行本不该有任何计算，但 LoRA 的分段逻辑没把它们认出来，真给假行施加了
完整 adapter delta，假行的 KV 槽被打成 NaN，下一层真实 query attend 到 NaN key
后整个真实 shard 全 NaN，输出从第一个 token 就是 `!0,0,0,0,1,0,1,` 这种数字汤。
这个 bug 的定位过程用了两层二分组合实验，值得单独展开，见 §四（`12cda1cd60`）。

**Bug 4：技能包中途被换人。** 槽位不够时逐出的策略偏向"保住 LoRA、牺牲 base"，
结果一个跑了 35 万字的长请求，做到一半背上的技能包被换了——后半段的笔记全是
"另一个人"写的。对照实验很漂亮：4 槽配置乱 2 次、逐出 5 次；5 槽配置 0 乱 0 逐出，
唯一变量就是槽数（`37fae98ed7`）。

这条线上还有一个值得记录的乌龙：**单机测试全过、上了 PD 集群就崩**，追了 20
个小时，最后发现是生产 prefill 启动脚本少了一个 `--lora-use-virtual-experts`
参数，走了没加固过的旧 kernel 路径。教训写进了手册：**做对照实验之前，先把两边
的启动参数逐条 diff 一遍。**（`cp-lora-crash-investigation.md`）

四层修完，乱码率明显下降。但还有。而且祸不单行，8 月 19-20 日 EAGLE 那边也炸了。

## 四、CP × LoRA：从首 token 乱码到 pad 行 NaN 毒化（8 月 21 日）

这是整个排查里方法论上最干净的一段。它示范了怎么用**两层二分组合实验**，
把一个"从第一个字就烂"的乱码，一步步钉死到具体的两层 LoRA 计算组合。

### 4.1 症状：从第一个字就烂

8 月 21 日，在前面几层 LoRA bug 修完之后，残留的乱码收敛成了一个很确定的签名：
**请求结果从第一个 token 开始就是乱码**，输出形如 `!0,0,0,0,1,0,1,`——一个感叹号
打头，后面跟着一串数字和标点。这不是"输出到一半变烂"，是**从第一个字就彻底烂**。

几个关键特征：

1. **首 token 恒为 id 0**。`output_ids[0] == 0`，logprob 返回 None。这说明不是采样
   抽到了烂签，是 logits 本身就是 NaN——`argmax(NaN) = 0`，模型"自信地"选了 0 号
   token（在词表里是 `!`）。
2. **filler prompt 复现率极高**：12 个 filler prompt + 20 个 topic prompt 的电池
   测试，乱码率 13-31/32（40%~97%），几乎必现。
3. **base 模型永远干净**（0/32 × 多轮）。
4. **乱码后状态持续**（"污染扩散"），不是偶发一次就好。

这个"首 token NaN"的签名和之前那些"输出到一半变烂"的乱码完全不同——后者是读到
错位置的旧记忆，前者是**前向计算本身算出了 NaN**。方向完全不同。

### 4.2 第一层二分：CP × LoRA 2×2 组合

第一个直觉：又是 LoRA。但 base 干净。那就把可能相关的两个开关（CP 和 LoRA）做
笛卡尔积，四种组合各跑一轮，每轮同样的请求、同样的权重、同样的温度：

| 组合 | CP | LoRA | 结果 |
|---|---|---|---|
| ① base | 关 | 关 | 干净（0/32） |
| ② 纯 LoRA | 关 | 开 | 干净（32/32） |
| ③ 纯 CP | 开 | 关 | 干净 |
| ④ CP + LoRA | 开 | 开 | **乱（13-31/32）** |

四种里只有第四种乱。一刀切掉了所有单因素假设：不是 CP 本身坏（③ 干净），不是
LoRA 本身坏（② 干净），是 **CP 和 LoRA 的组合**——两个子系统单独都正确，叠在一起
才出问题。这种 bug 最难查，因为每个子系统的维护者都会说"我这边单测过的好好的"，
而他们没说错，问题出在两个子系统的**接缝**上。

### 4.3 第二层二分：LoRA 模块族组合

CP×LoRA 定罪后，下一个问题：LoRA 有几十层（attention 的 q_a/q_b/kv_a/kv_b/o_proj
+ MoE 的 gate/up/down），是哪几层和 CP 组合出的问题？总不能一层层试。

我们用了一个运行时模块族二分工具（`SGLANG_LORA_FAMILY` 环境变量，`lora_manager.py`
里加的），**不需要重新打包 adapter 权重**，一个 env 切换就能选择只给哪些模块族
施加 LoRA delta。四组单臂（kv_a / q_b / o_proj / kv_b）先各自跑：

| 单臂 | 结果 |
|---|---|
| kv_a only | 干净 |
| q_b only | 干净 |
| o_proj only | 干净 |
| kv_b only | 干净 |

四个单臂全干净。然后两两组合：

| 组合 | 结果 |
|---|---|
| **kv_a + o_proj** | **乱（13/32）** ← 最小犯罪组合 |
| kv_a + q_b | 干净 |
| kv_a + kv_b | 干净 |

**kv_a + o_proj 是最小犯罪组合**——单独都不坏，合在一起就坏。这就是"两层计算
组合有问题"的精确含义：不是某一层 LoRA 坏了，是 kv_a 和 o_proj 这两层 LoRA delta
**同时施加在 pad 行上**时，才产生 NaN 并传播到真实行。

为什么是这两层？原理是这样的：

- **kv_a** 是 attention 的 K/V 投影。它写出的 K、V 会存进 KV cache，**包括 pad 行
  的 K/V 槽**。如果 pad 行被施加了 LoRA delta，delta 作用在 pad 行的垃圾激活上
  （freed-memory 残留，量级 ~1e-9），浮点运算后可能产生 NaN——这些 NaN 就写进了
  pad 行的 KV 槽。
- **o_proj** 是 attention 的输出投影。attention 的输出 = softmax(Q@K^T) @ V，如果
  K/V 里有 NaN（来自 kv_a 写的 pad 行槽），整个 attention 输出就是 NaN。o_proj
  再把这个 NaN 输出写进 hidden state，**NaN 就从 attention 层传播到了下一层**。
- 单独 kv_a：NaN 写进了 K/V 槽，但如果 o_proj 没有 delta，attention 输出经过
  o_proj 的 base 权重（无 delta）后，NaN 可能被残差连接稀释或被后续层吸收
  （取决于具体数值路径），不一定稳定传播。
- 单独 o_proj：o_proj 有 delta 但 K/V 是干净的（kv_a 无 delta），attention 输出
  有限，o_proj delta 作用在有限值上不会产生 NaN。
- **只有 kv_a + o_proj 同时有 delta**：kv_a 产生 NaN 源（pad 行 K/V），o_proj 把
  NaN 稳定传播到 hidden → 下一层全 NaN → logits NaN → argmax=0 → `!`+数字汤。

这个"最小犯罪组合"的发现非常关键，它把排查范围从"几十层 LoRA"缩小到了"这两层
的 delta 同时作用在 pad 行上"这个精确场景。

### 4.4 根因：pad 行被施加 LoRA delta → NaN 毒化真实行

有了"kv_a + o_proj + CP"这个三角定罪，根因就清楚了。原理分三步：

**第一步：CP 产生 pad 行。** CP round-robin 把 batch 撕成 cp_size=8 段，如果 token
数除不尽（比如 29 个 token），要补到 32（8 的倍数）：

```
N_real = 29,  cp_size = 8
N_pad  = cp_size - (N_real % cp_size) = 8 - (29 % 8) = 8 - 5 = 3
N_batch = N_real + N_pad = 32   （pad 行 = [29, 30, 31]）
```

这些 pad 行是假数据，本不该参与任何计算。

**第二步：pad 行被归属给最后一个请求，施加了完整 LoRA delta。** `_cp_shard_row_request_ids`
把 pad 行归属给最后一个请求（不是丢弃），于是 shard 视图的 LoRA segments 把 pad 行
当成真实行，对它们施加了完整的 adapter delta。pad 行的激活是 freed-memory 残留
（量级 ~1e-9），LoRA delta 作用上去后：

```
delta_output = W_down @ activation(~1e-9) @ W_up
```

这个运算在浮点下可能产生 inf/nan（取决于具体路径），结果就是 **pad 行的 KV 槽
被写成了 NaN**。

**第三步：NaN 经 KV 传播到真实行。** 这是毒化的关键——pad 行和真实行在同一个
attention 的 KV 里。下一层的真实 query 做 `Q @ K^T` 时，K 里有 pad 行的 NaN：

```
scores = Q @ K^T          # K 的 pad 行是 NaN → scores 对应列 = NaN
attn   = softmax(scores)   # NaN 传播 → attn = NaN
output = attn @ V          # V 的 pad 行也是 NaN → output = NaN
hidden  = hidden + o_proj(output)   # NaN 进 hidden
```

逐层 dump 证据（`--debug-tensor-dump`）铁证如山：

- **layer-7 MoE gate**：NaN **仅在 gather 后 32 行的 pad 行 [23, 27, 31]**（29 真实
  token 对齐到 32，pad 行是最后那几个）；
- **layer-8 attention 输出**：**4 个真实行全 NaN**——NaN 从 pad 行的 KV 槽经 attention
  传播到了所有真实行；
- **logits**：全 NaN → `argmax(NaN) = 0` → token id 0 → `!` + 数字汤。

MLA-AUDIT 探针（`SGLANG_MLA_AUDIT=1`，`forward_mla.py`）进一步确认：kv_a+o 组合下
audit 计数暴涨到 **7821**（正常为 0），且 hidden=NaN 从 layer 1 起就出现。

**为什么 base 干净 / CP-off 干净**：
- base 模型不施加任何 LoRA delta，pad 行的 KV 是 base 权重算出的有限值，不产生 NaN；
- CP 关掉就没有 padding（N_batch = N_real，没有 pad 行），没有 NaN 源头；
- 只有 CP + LoRA 同时存在，pad 行才会被 delta 打成 NaN，再经 KV 传播毒化真实行。

**随机性来源**：pad 行的激活是 freed-memory 残留，内容取决于分配器复用了哪块内存
（~1e-9 量级的垃圾值），所以同一个请求重放有时 NaN 有时不 NaN（取决于那块内存
上次被谁用过、哪些 rank 带 pad）。这解释了 13-31/32 的波动复现率。

### 4.5 修复：pad 行映射到 base 槽（零 delta）

修复（`chunked_backend.py`，commit `12cda1cd60`）的核心思路：pad 行保留 -1 哨兵，
映射到 **adapter slot 0（base 槽）**。`lora_ranks[0] == 0` 意味着 base 权重，所有
LoRA kernel 对 rank-0 segment 早退 no-op——pad 行收到零 delta，KV 槽是 base 权重
算出的有限值，不产生 NaN。同时 segments 保持覆盖全行（与验证过的结构一致）。

```
pad 行 → lora_rank = 0 (base) → LoRA kernel early-return → delta = 0 → KV 有限值 ✓
真实行 → lora_rank = adapter_id → 正常施加 delta → KV 正常 ✓
```

第一版尝试把 pad 行**排除**出 segments（permutation 短于 x），结果 warmup 即 IMA
（absorbed step kernels 未验证过 permutation < x_rows 的结构）→ 回退，改用 slot-0
映射。教训：**改 segment 结构必须保持 `covered == x_rows` 不变量**。

同 commit 的伴随修复：`deepseek_mla_correction.py` 的 `_get_state` 改走
`_resolve_batch_info(x_rows)`（absorbed kv_b 修正此前拿 full 视图路由 shard 张量）；
`virtual_experts.py` shrink kernel 拒绝负 offs_token（freed-memory 垃圾在 align slack
里越界写）。

验收（1101/1100 测试对，完整 L0 + CP on + 生产 flags）：电池（12 filler + 20 topic）
×3 轮 **0/96 乱码**；MLA-AUDIT 计数 **0**（乱码时 7821）。

### 4.6 这段排查的方法论小结

1. **两层二分组合**：第一层 CP×LoRA 2×2 矩阵定罪"组合才坏"，第二层 LoRA 模块族
   二分（kv_a+o 最小犯罪组合）定罪"哪两层计算组合坏"。比逐层读码快一个量级。
2. **运行时模块族二分**（`SGLANG_LORA_FAMILY`）：一个 env 切换就能选哪些模块族施加
   delta，零 adapter 重打包，把"几十层 LoRA 哪层坏"的验证从小时级降到分钟级。
3. **逐层 dump 的行级 NaN 分析**是定位毒化传播的金标准：pad 行 NaN → 真实行 NaN
   的传播链，一眼看出毒化方向。
4. **"首 token NaN"和"中途乱码"是不同 bug**：前者是前向计算本身算出 NaN（pad 行
   毒化），后者是读到错位置的旧记忆（索引错位）。方向完全不同，不能混为一谈。
5. **混沌系统里盯质性签名**：pad 行激活是 freed-memory 垃圾，复现率天然波动
   （13-31/32），盯数值幅度没意义，盯 **NaN/零化的质性签名**才稳。

## 五、draft 崩溃与 accept 断崖（8 月 19-20 日）

这其实是另一条独立线索，讲它是因为它教会了我们 DCP 的"虚拟门牌号"体系——终局
真凶就住在这里。

先是一串 CUDA Xid 31 崩溃（GPU 访问了非法地址）。py-spy 加设备断言一路追，
发现草稿模型每次开猜之前要从 `req_to_token` 表里抄一份"我的笔记存在哪些格子"
的清单，抄的时候偶尔会抄到撕裂的旧数据，拿到一堆超出池容量的垃圾格子号。
演化成三段式：第一阶段直接崩；第二阶段只把写入端消毒，不崩了，但垃圾格子号
混进了空闲列表，**分配器永久中毒**——表现为 accept 从 3.0 一路掉到 1.0 再也不
回头；第三阶段在源头把清单钳在合法范围，才真正结案（`0e5f7704e1`）。

接着 accept 掉到 0.07，几乎全拒收。这次是**虚拟门牌号**的问题，值得用一段话
讲清楚，因为终局真凶就住在这里：

> DCP=4 的 decode，每张卡只保管四分之一的笔记。但请求的清单表 `req_to_token`
> 里存的是**统一的虚拟门牌号**：虚拟页 256 = 物理上第 4 页归 0 组、第 4 页归
> 1 组……即"虚拟页号 v 的物理位置 = v 除以 4，归 v 除以 4 的余数那组管"。
> 所有写入和读取都必须做这个换算，而且**只能做一次**。当时代码里有的地方换算了
> 两次（等于除了两次 4），有的地方把合法虚拟号当越界垃圾消毒掉了，还有 merge
> 上游版本时把草稿池从 7.4M 格偷偷缩回 1.85M 格，虚拟门牌大面积越界。
> 三张补丁（`9db63a6abb`、`371a991947` 等）把整条链统一成"虚拟号全程保留，
> 只在真正碰物理池的那一下换算"。

这条线还顺手纠正了一个错误认知：以前觉得单请求 accept 5.9（每猜必中）是"状态
好"，实际那是**复读机病征**——草稿沿着退化轨道走，目标模型全盘接受，输出全是
重复。健康区间是 2.2~3.2。（`dcp-virtual-id-domain-fix.md` §6）

draft 线修完，崩溃停了，accept 回到健康区间。但乱码还在。而且这时候有人注意
到一个可怕的细节：**把 EAGLE 整个关掉，乱码还在。**

---

## 六、推翻一切的那个上午（8 月 22 日）

8 月 22 日凌晨到上午，做了三组消融实验，每组都要"改配置、重启、等五分钟预热、
灌同样的真实流量"，一轮二十到四十分钟，而那条公网链路当天还在劣化（RTT 从
半秒涨到 7 秒），每轮实验都被拖长。

**第一锤：base 模型也乱。** 我们在本地架了个录制代理，把打向测试集群的流量
强制改写成"不带任何 LoRA"的纯底座请求。乱码照样复现。**"只有 LoRA 有问题"
这个从第一天起引导所有人的前提，死了。**

**第二锤：关掉 CP，还乱。** 这是最意外的一锤。CP 的行对齐嫌疑最大（上游源码
里甚至有一行注释承认"CP 和多请求批次目前有精度问题"），而且当时刚做的一个
CP 整除门修复在测试对上"28 连发零乱码"过。结果 CP 整个关掉，乱码依旧。
那个"28 连发零乱码"其实是我们撞上了另一个 bug 的静默期（后面会讲）。**CP，死了。**

**第三锤：关掉 DCP，干净了。** decode 从"四组各管四分之一笔记"退回"一组管全部"，
同样的流量，怎么打都不乱。多轮反复验证，结论稳定。**DCP 定罪。**

同一天上午还破了一桩冤案，值得写进来提醒所有人：有段时间流式输出的间隔越来
越大，看起来像"decode 性能断崖"。分层排查后发现引擎日志里每秒吞吐一直正常，
真正的原因是（1）机房公网劣化到 0.37MB/s，（2）我们的取证代理给每个请求强制
注入了 top-5 logprobs，把流式载荷放大了三到五倍，两边一叠加，数据在管道里
排队。**看到"变慢"，先分清是算得慢还是送得慢**——引擎日志和客户端体感必须
对照着看。

## 七、终局：DCP 双 bug（8 月 22 日下午）

DCP 定罪后，我们同时放出五个并行的调查 agent（分别啃：注意力元数据生命周期、
Triton kernel 数学、KV 传输与页归属、索引构建链路、git 历史考古），人则同时
做独立分析。三路独立收敛到了同样的两个 bug，都在索引器周边。

**真凶 A：索引卡片的门牌号换算只做了一半（主犯）。**

回忆第一节：DSA 索引器给笔记的每一页算一张"索引卡片"（index_k），存在池子里，
将来打分挑页全靠它。DCP=4 时每张卡的存放位置要做虚拟号到本组物理槽位的换算
（`虚拟号 x → (x÷256)×64 + x mod 64`，粗略这么理解）。旧代码里有个"优化判断"：
**"小于本组池子大小的编号，肯定已经是本地物理槽位了，直接存"**。

这个判断听起来很合理，实际上是错的：分配器发放的虚拟号是**从 0 开始往上递增**
的，而本组池子大小是 1.85M。也就是说，进程刚启动、水位还低的时候，头几个大
请求拿到的虚拟号全部小于 1.85M——**全部走了直通分支，全部没换算，索引卡片
全部存错格子**。索引器拿着错位的卡片去打分，稀疏注意力挑出来的 2048 页就是
错的页。模型读错笔记，自信地胡说。

这个 bug 狠在哪：

- 它**越界但不越到非法区**（错格子也是合法格子），不崩、不报警、日志一片祥和；
- 水位涨过 1.85M 之后直通分支自然失效、换算分支接管——**bug 自己好了**。这
  一条同时解释了"重启 decode 能缓解"（水位清零重新进入坏窗口）、"长请求尾部
  自愈"（尾部 token 的卡片是在水位越过线之后写的）、"概率性"（取决于请求落在
  水位线的哪一侧）；
- 它同时祸害 base 和 LoRA，但因为 LoRA 线上流量长上下文多、缓存挤占频繁触发
  重算，看起来"只有 LoRA 乱"，把我们骗了整整三天。

修复很小（`5974a4fc56`）：去掉那个"优化判断"，所有编号无条件做完整换算，和主
KV 的写入路径用同一套公式。为了防止这类问题再溜走，还把诊断计数器挪到了修复
动作**之前**——原来的计数器放在修复之后，数到的永远是修好的数据，恒为零，
等于瞎了。

**真凶 B：选页清单的空位被钳到了 0 号柜（从犯）。**

索引器每行要交出 2048 个页号。DCP=4 时每张卡只有四分之一的页可挑，于是上下文
短于约 52 万字的请求，本组页数不足 2048，清单里会留一些"空位"，值是 -1。正确
处理是让注意力跳过空位。但实际上有一条快速路径把清单直接喂给了 NVIDIA 的
trtllm kernel，而下游有个"保底"操作把所有 -1 **钳到 0 号格子**——0 号格子里
存的是完全无关内容的 KV。我们用一个对照实验定罪：让某组一行页都不拥有（清单
全空），kernel 返回的归一化系数是 0 而不是"负无穷"——**证明它对每个空位都真
的做了注意力计算，没有任何跳过**。最坏情况：四分之三的注意力预算花在同一个
陌生人的记忆上。

修复：空位不再钳 0，改指向**本行自己的第一个有效页**（这行打分最高的页），
多算几次自己的头名种子，数学上只是权重略偏，不再引入任何外部内容。

两个补丁部署到测试对（DCP=4 + EAGLE 开），之前 37%~50% 乱码的流量持续干净；
当天傍晚部署到生产 1P2D（1100/1103 两台 decode），公网验证通过。

部署当天还有两个小插曲，一并如实记录：两台 decode 在新进程跑了 8.5 分钟后
同时自己退出了（查了登录日志、OOM 记录、定时任务，都不是人为，真实原因的
堆栈被下一次重启覆盖丢失，成了悬案，已改流程要求重启前先备份日志）；以及
一次"重启 proxy"实际根本没杀掉旧进程（端口匹配没生效），旧 proxy 一直活得好
好的，虚惊一场。

## 八、为什么这么难

事后看，每个 bug 都"显然"。事中难，难在这几件事：

**症状同质化。** 三个不同层面的真 bug（cuda graph 残影、缓存串柜、索引错位）
吐出来的乱码长得一模一样。修掉一个，症状减轻但不消失，你不知道是"修的不彻底"
还是"另有一个"。我们先后三次认为"结案了"，三次重新开案。

**概率性是天然的谎言放大器。** 复现不稳定，任何"修完跑了 28 连发没乱"都不能
下结论——可能只是撞进了另一个 bug 的静默窗口（CP 整除门那次正是如此）。后期
我们立了规矩：任何修复的验证，必须先让系统进入"容易乱"的状态（低缓存水位、
长上下文、强制重算），再谈干净。

**系统是活的。** 排查期间同时发生的干扰：公网劣化到 0.37MB/s（让一切实验变慢、
还制造了假的"性能断崖"）、一次真实的编译器 bug 假警报、日志被重启覆盖、
proxy 半死不活。每一条都要花时间证伪。

**排查成本不对称。** 一轮 A/B 消融 = 改配置 + 重启（4~5 分钟预热，EAGLE 要重新
录 cuda graph）+ 灌流量 + 人肉检查输出（乱码是全谱系的，从"几个字不对"到
"整段模板汤"，正则只能抓最极端的，轻度退化只能靠人读）。五天里这样的轮次
做了几十轮。

最后说一句公道话：这套系统没有白折腾。五天 41 个 fix 里，除了终局这两个，
其余的也都是真 bug（崩溃、泄漏、死锁、400、断流），只是都被"乱码"这个最响的
症状盖住了。明细都在 `docs/agent/` 下的 19 篇调查文档里，每一篇有证据链、
复现步骤和判据命令，下次再出类似的事，按图索骥。
